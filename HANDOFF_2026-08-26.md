# GeneWriter — Session Handoff, 2026-08-26

Two shipped changes, both about the same thing from opposite ends: **the
population is sized for the steady state, and the run dies in the
transient.** Read `HANDOFF_2026-08-20.md` for the GA design context and
`DESIGN_default_schedule.md` for the schedule this is clearing the way for.

Neither change alters what the GA searches for. Both change how large the
search is allowed to get at any one instant, which is what has actually
been killing real Colab sessions.

---

## 0. The shape of the problem

Every sizing knob in the codebase before today answered *"how many
individuals should the population hold?"* — `suggest_population_size()`,
`"select"`'s `target_size`, `"input"`'s `count`. That is the
**steady-state** size, and it is only the right question when the steady
state *is* the peak.

It never is. The population is at its largest at two moments, neither of
which any of those knobs governed:

| moment | how big | what governed it before today |
|---|---|---|
| just after seeding, before the first cull | as many seeds as RAM holds | nothing |
| mid-growth, before any cull | `len(pop) × (1 + rate)` | nothing |

Both are *transients*: they last one step, they are several times the
number the schedule is written in terms of, and they are the numbers that
have to fit in RAM. Sizing the steady state to fill half of RAM and then
letting a growth step multiply it by 5 lands at 2.5× available memory —
which is not a crash you can debug from the traceback, because on Colab
the process is simply killed.

§1 closes the first row. §2 closes the second.

## 1. Shipped: seed wide, keep narrow

### The problem

`"input"`'s `count` auto-sizes to whatever RAM allows
(`suggest_population_size()`), and for a biological-length protein that
number is enormous. **That is correct for seeding** — coverage of a
10^N-genotype space is the one thing random seeds are for, and a hand-picked
2000 was already shown to under-test a real target
(`memory/schedule_sequence_space_clamping.md`).

It is wrong for everything after seeding. The very next `"growth"` step
multiplies that population by `rate` before any `"select"` runs. Luke hit
this live in Colab; the manual workaround was inserting a
`{"kind": "select"}` immediately after the seed step.

### The fix

That workaround is now a first-class param rather than a hand-edit.

**`"input"` gained `keep`** — an optional cap on how many distinct
individuals survive seeding. Same soft weighted `select_survivors()` cut,
same `sequence_space_size` clamp, same absolute-population meaning as
`"select"`'s `target_size`. Omitted keeps every distinct seed, so every
existing and saved schedule is unaffected.

```python
{"kind": "input", "keep": 5000},          # count still auto-sizes to RAM
```

**Why on `"input"` rather than "write a `select` step next"**: a following
`"select"` would `refresh_change_vectors()` over the whole freshly-seeded
population first (the module's refresh-first convention), recomputing
exactly what `seed_population()` just computed — over the largest
population the run ever holds. That is the single most expensive redundant
refresh available in a run. `keep` cuts on the vectors already in hand.
There is a test asserting the refresh does *not* happen, with the separate
`select` as the contrast case, because the reasoning is the entire
justification for the API shape.

The one case where a separate `select` is still right, and it is in the
docstring: seeding **into** an already-evolved population whose vectors
have drifted since the last exact checkpoint. `keep` would score those
carried-over individuals on whatever approximate vectors they arrived with.

**`run_ga` applies `target_size` right after seeding**, not one growth step
later, whenever it is set below the seed count. Same defect in the other
run mode: `num_seeds` also auto-sizes, and generation 0 would grow every
one of those seeds by up to 10× before the cap first bound — an
order-of-magnitude peak in the one generation where the population is
largest and least selected.

Both drivers now set the cap explicitly (`keep` / `target_size`), with
guard tests asserting they keep it. `"input"`'s `count` and the *final*
`"select"` stay auto-sized: nothing grows after that final select, so it
can safely take everything RAM allows.

## 2. Shipped: RAM-aware growth rates

### The problem

A growth step allocates `len(pop) × rate` new `Proposed_Solution` objects
**all at once**, before any `kill_off`/`select` culls them. Nothing priced
that. A schedule asking for `rate=5` on a population sized to fill half of
RAM asks for 2.5× the machine, and gets an OOM kill rather than an
exception.

`chunk_size` (VRAM-aware, landed 2026-08-19) already bounds the *GPU* side
of a step. This is the host side — where the population itself actually
lives, for the whole life of the run.

### The fix

Expansion steps now measure before they expand, and turn themselves down.

```
[directed_growth] replicating 20,000 individuals at rate 5 would allocate ~2.2 GB of new
solutions, but only ~563.2 MB of free host RAM is budgeted for it (ram_fraction=0.5,
~23.4 KB per individual). Reducing rate 5 -> 1 to stay inside it. The run continues, but
it is searching less broadly per generation than the schedule asked for -- the durable fix
is a smaller select/keep target_size (or more RAM), not this rate.
```

New in `ga.py`, next to `suggest_population_size()`:

| name | what it does |
|---|---|
| `suggest_growth_rate(pop_size, …)` | `budget // bytes_per_individual // pop_size`, floored |
| `clamp_growth_rate_to_ram(requested_rate, …)` | applies that as a ceiling, warns when it binds |
| `warn_if_expansion_exceeds_ram(projected_new, …)` | warning-only, for steps with no rate to lower |
| `expansion_ram_budget_bytes(ram_fraction)` | `available_ram_bytes() × ram_fraction` |
| `PopulationRamWarning(UserWarning)` | own category — filterable, assertable |
| `DEFAULT_GROWTH_RATE` / `DEFAULT_GROWTH_RAM_FRACTION` | `10` / `0.5` |

The floor is the whole point: headroom for 4.5 means a rate of 4. Rounding
the other way is exactly the OOM being avoided.

### Four decisions worth knowing about

**The budget is not reduced by the resident population.**
`available_ram_bytes()` reports what is still *free*, so the population's
own footprint is already excluded from it. Subtracting it again would
double-count and shrink every growth step by the size of the very thing
being grown. Reading it fresh per step (rather than computing one budget at
the top of a run) is also what makes it self-correcting: a schedule whose
earlier steps left more resident sees a smaller budget on the next step,
automatically.

**The rate floors at 0, not 1.** If not even one replicate each fits, the
step is skipped, with its own distinctly louder warning. Forcing a rate of
1 would still OOM — it just doubles the population instead of sextupling
it. Skipping is survivable *and* self-correcting inside a schedule: growth
no-ops, the following `kill_off`/`select` shrinks the population, and the
next growth step finds room again. The step still advances `step_count` and
checkpoints, so a saved run's generation numbering does not silently shift
under a no-op.

**The warning is the feature, not a side effect.** A silently reduced rate
is a *different algorithm*, not a slower one — fewer offspring per
individual is a narrower search per generation. Whoever reads the output
needs to know their schedule asked for more population than the machine
has, because the durable fix is a smaller `select`/`keep` target, not a
rate the library picked for them. Every message names the step, both rates,
the projection, the budget, and the actual remedy.

**`flatten` warns but does not clamp.** It has no rate to lower: how far it
expands is set by the replicate mass the population has already
accumulated, and `recursion_limit` does not move that ceiling (each
`_flatten_round` conserves the total count; only the final collapse-to-1
changes it). Silently doing less would misreport what ran, so it projects,
reports, and proceeds.

### Wiring

- **`schedule._do_growth`** clamps immediately after the existing
  `_remaining_space` clamp — the two are exact parallels ("no more
  replicates than the sequence space has left" / "…than RAM has"), and
  both growth step kinds route through it.
- **`ScheduleContext`** gained `ram_fraction` plus a
  `bytes_per_individual()` method that caches the measurement. The
  measurement builds and scores a throwaway seed; a `repeat` block with
  five growth steps would otherwise pay for five identical measurements of
  a number that cannot change during a run.
- **Per-step override**: `params.get("ram_fraction", ctx.ram_fraction)`, so
  key-absent means "use the run default" and key-present-as-`None` means
  "off for this step". `None` at either level is a true no-op — it skips
  the measurement too.
- **`run_ga`** gained `growth_rate` and `ram_fraction`, re-clamped every
  generation (both the population size and the free RAM move), and now
  passes `nreplicates=rate` explicitly instead of relying on the implicit
  default of 10.
- **Both drivers** got a documented `RAM_FRACTION=0.5` knob threaded into
  both run modes.

## 3. A real bug this surfaced: sizing was consuming the RNG stream

Adding the clamp immediately broke
`test_run_ga_growth_batching_matches_reference_merge_path`, and the cause
was not in the new code.

`estimate_bytes_per_individual()` measures a real `Proposed_Solution` by
building one with `generate_seed()` — which draws from the global `random`
stream. **A measurement was changing what the run then did.** A seeded run
produced different results depending on whether a sizing default happened
to be consulted.

This was latent in `suggest_population_size()` from the day it landed
(2026-08-19). It stayed invisible because it only ever ran once, at setup,
before anything reproducible started. It surfaced the moment something
called it *inside* the generation loop.

Fixed by wrapping the seed build in `random.getstate()`/`setstate()`, with
a regression test
(`test_estimate_bytes_per_individual_leaves_the_random_stream_alone`) and a
docstring paragraph saying why a measurement helper must be RNG-neutral.

Worth generalizing: **anything called for its return value rather than its
effect should leave the RNG where it found it.** The GA has several such
helpers, and this class of bug is invisible until a seeded comparison test
happens to straddle the call.

## 4. Testing

**517 passing** (WSL, ~157s), up from 490. 27 new tests.

The RAM tests all pin `available_ram_bytes()` to a chosen figure rather
than reading the real machine's, with a `_budget_for(pop_size, rate,
bytes_per_individual)` helper that inverts `suggest_growth_rate()`'s
arithmetic — so each test states the situation it wants ("room for exactly
4.5 replicates each") instead of carrying a hand-computed constant, and
means the same thing on a laptop, in CI, and on a Colab VM.

Coverage worth knowing exists:

- the 4.5 → 4 floor, and 0 when nothing fits, as separate cases with
  separate warning text;
- both growth step kinds, asserting on the `nreplicates` the reproduction
  functions actually receive — the final population size would mask the
  difference entirely once `select` runs;
- the no-headroom path returning the population intact rather than raising;
- `ram_fraction=None` as a true no-op at step, context, and `run_ga` level,
  each asserting *no* warning was emitted (a warning that fires when it
  should not is as bad as one that does not fire);
- the footprint measured exactly once across a three-growth-step schedule;
- `keep` not refreshing change vectors, with a separate `select` as the
  contrast that does.

Two driver guards were added on top: one asserts `RAM_FRACTION` is a usable
share, one greps `run_pipeline`'s source for both call sites — an unwired
knob otherwise reads as working (no error, sensible value in `CONFIG`)
while the run it is meant to protect quietly keeps the library default.

## 5. Found while working, not fixed

### 5.1 The notebook's driver cell is not a copy of the script

`Testing_GeneWriter.ipynb`'s driver cell and
`scripts/colab_stress_test.py` have **diverged in both directions**. The
notebook carries the live Colab config (real Drive paths, `GENE_ID=5350`,
the ngram model path) — expected — but it is also *ahead* of the script in
places: it has `CHUNK_SIZE` and `REGENERATE` options the script does not.

Consequences, both live:

- Notebook edits must be surgical. Re-pasting the script over that cell
  would silently revert a working setup. (Mechanically: json-escape the
  fragment and replace it in the raw `.ipynb` text — a `json.load`/`dump`
  round trip reformats the whole file and buries a three-line change in a
  whole-file diff.)
- Only the script is test-guarded. `tests/test_colab_stress_test.py`
  imports `scripts/colab_stress_test.py`; **nothing at all checks the
  notebook copy**, which is the one that actually runs in Colab.

Cheapest fix if this keeps costing time: a test that parses the notebook,
extracts the driver cell, and runs the same config assertions against it.
It cannot check for drift in the *code* half of the cell, but it would
catch a stale or malformed config — which is the failure mode that has
actually happened (`memory/colab_stress_test_stale_paste_oom.md`).

### 5.2 `default_schedule()` still needs the peak multiplier

`DESIGN_default_schedule.md` §6.6 remains open and is now the *last*
unpriced peak. It is a different problem from §2 above: an EXPLORE macro
deliberately inflates the population across *several* steps (`flatten`
multiplies distinct individuals, `kick` adds colonists, and neither
selects), so the peak lands mid-cycle at 2–3× the steady state.

The machinery is further along than that design assumes:
`suggest_population_size()` has a `peak_multiplier` parameter, and both
`"input"` and `"select"` already accept it as a step param and pass it
through. What is missing is any schedule that *uses* it — the number has
to come from the schedule's shape, and no builder exists to know it.

The per-step clamp from §2 is a backstop, not a substitute. It will keep a
run alive by turning rates down, but a schedule that needs its rates turned
down every cycle is one whose steady-state size was chosen wrong. Measure
the real factor with the `report` step (§2.5 of that design) rather than
trusting the 3.

### 5.3 `explore()` / `exploit()` / `default_schedule()` are referenced but do not exist

Six docstrings across `ga.py` and `schedule.py` point at
`schedule.explore()`, `schedule.exploit()`, and
`schedule.default_schedule()` as though they were built —
`suggest_population_size()`'s `peak_multiplier` docs say
"`schedule.default_schedule()` passes its own `DEFAULT_PEAK_MULTIPLIER`",
`release_protection`'s say "see `schedule.explore()`/`schedule.exploit()`,
which pair every…". None of the three is defined anywhere.

`b37d7fe`'s commit message ("Added `explore()` and `exploit()` macros for
simplicity") overstates what landed: the *primitives* those macros need
went in — `release_protection`, `kill_off_by_term`, `protect` — and the
docstrings were written forward against
`DESIGN_default_schedule.md` §3.2's sketch, but the macros themselves were
not written.

Not urgent, and the forward references are arguably useful as design
intent — but they read as descriptions of existing API, which is a trap for
anyone (or any future session) reading the docstrings as a map of what is
callable. Either build the three functions or mark the references as
planned.

### 5.4 The RNG-neutrality question is broader than one function

See §3. Nothing else is known to be affected; nothing else has been
checked either.

## 6. Where this leaves the roadmap

`DESIGN_default_schedule.md` §5's build order is unchanged, and its first
two items are still the gate:

1. `report` step + `pressure_entropy()` — free, and it makes every claim in
   that design falsifiable. Plot entropy against the existing t-SNE before
   building anything that depends on "stuck individuals cluster".
2. `release_protection` — **already built**, landed in `b37d7fe`. That
   blocker (§6.1 of the design) is closed.
3. `kick` with sampled k=2.
4. `explore()` / `exploit()` / `default_schedule()` — see §5.3; these are
   documented as though they exist and do not, so this step is both a
   build and a cleanup. Then the equal-budget comparison against the
   current default.

What today changed for that plan: the memory-pressure objection to running
any of it at real scale is now handled at the step level. A schedule that
overruns degrades — loudly, with the numbers, and naming the fix — instead
of taking the VM down mid-run.
