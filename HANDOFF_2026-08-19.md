## 1. Special-translation corrective pass (epitranscriptomics)

Scoped and built a second-pass corrective pipeline for real human genes
whose actual protein differs from naive genomic-DNA translation —
deliberately kept separate from `GeneDataSourcing.ipynb` (which stays the
simple, high-throughput, unmodified main sourcing path per Luke's explicit
architecture call).

- **Selenocysteine recoding**: all 25 human selenoprotein genes
  (`SELENOPROTEIN_GENE_IDS` in `src/genewriter/special_translation.py`) —
  an in-frame UGA gets recoded to selenocysteine instead of terminating
  translation. Fix: a codon table with UGA moved (not duplicated) from `'*'`
  to a new `'U'` entry.
- **Non-AUG start codons**: MYC and TXNRD3 (both literal CTG at their real
  start) — `check_cds_against_protein_at_position()`, anchored at NCBI's own
  annotated CDS start rather than a literal-ATG search.
- **Programmed ribosomal frameshifting**: OAZ1 (+1 shift, pinned to the exact
  nucleotide — its ORF1/ORF2 UGA junction) and PEG10 (-1 shift, pinned to
  the literal genomic heptamer `GGGAAAC`, the textbook retroviral-style
  slippery sequence). `apply_frameshift()`/`apply_frameshift_to_exons()`
  reconstruct both genes' real proteins exactly, byte-for-byte, including
  correct genomic codon *positions* (not just the right amino acids) via a
  splice applied to the real exon-fragment list, not just a flat string.
- **A-to-I (ADAR) and C-to-U (APOBEC1) editing**: investigated live against
  real NCBI data (GRIA2, GRIA3, GRIK1, GRIK2, CYFIP2, BLCAP, APOB) and found
  NOT to need corrective handling — for every one, standard genomic
  translation already matches NCBI's canonical protein exactly (even
  GRIA2's famous Q/R site comes out unedited/Q). NCBI's RefSeq protein
  reflects the genomically-encoded, unedited form for these genes — no
  sourcing bug, just a corpus-completeness gap (synthesizing the edited
  variant would mean inventing a protein not backed by any real RefSeq
  record — a fundamentally different, more speculative task, not attempted).
- **Stop-codon readthrough**: not investigated this session.

Shipped as `src/genewriter/special_translation.py` +
`SpecialCasesCorrectivePass.ipynb` (repo root), verified end-to-end against
real downloaded NCBI data (not just synthetic tests) for all 25
selenoprotein genes + MYC + OAZ1 + PEG10 (3 isoforms). Full detail:
memory `special_translation_corrective_pass.md`.

**Not done yet**: actually running the corrective sweep against the live,
full corpus (only run against small scratch/verification batches so far),
and GA-side mutation safety (nothing currently stops the GA from
codon-optimizing *through* a Sec/SECIS site, non-AUG start, or frameshift
junction — see memory `future_work_items.md` item 6). Both deliberately
deferred until the GA/baseline pipeline itself was working smoothly — which,
per §5 below, is now true, so this is a reasonable next thing to pick up.

## 2. Patent-neighborhood similarity visualization

Sales-case feature: given a specific sequence a patent attorney wants to
file on, show how much of the GA's viable output population falls within
various nucleotide-identity bands (99.9%/99%/95%/90%/85% by default) of it.

Shipped in `src/genewriter/visualize.py`:
`nucleotide_identity_to_reference()` (literal nucleotide-level % identity,
deliberately not the coarser codon-choice Hamming distance the rest of the
module uses — two different codons sharing 1-2 of 3 nucleotides count as
partially identical, matching how nucleic-acid sequence claims actually
report identity), `similarity_band_counts()` (cumulative per-threshold
counts), `plot_population_similarity_to_reference()` (reuses the existing
t-SNE embedding for spatial layout, discretely colors by band). Band
counts are computed against the *full* population even when the plot
subsamples for rendering, so the numbers reported are always exact.
Verified by actually rendering a figure against synthetic data with real
spread across bands, not just unit tests.

## 3. Weight-calibration asymmetry fix

Luke's own catch: `weight_calibration.py`'s intolerance weights (how much
each change-vector term should matter, derived from how tightly nature
conserves it) were based on plain `std / |mean|` — silently assumes
symmetry. For a skewed baseline (e.g. CodonPairBias, already known
Boltzmann/gamma-shaped), this doesn't just get distorted, it can become
outright uninformative: an exponential distribution has `std == mean` by
mathematical necessity, so CV sits at ~1.0 for that whole family regardless
of actual tightness.

Fix: `distribution_fit.FittedDistribution` gained `value_at_zscore()` (the
inverse of its existing `transform()`), and `term_coefficients_of_variation()`
now reads the raw value one normal-equivalent std above/below the *fitted*
center and averages the two half-widths, instead of raw sample std/mean.
Reduces to the exact old value for a genuinely Gaussian baseline (same
"no change for normal baselines" principle the rest of `distribution_fit.py`
already follows). Comment left in the code, verbatim per Luke's own framing:
this determines a single scalar per term regardless of distribution shape,
may need tuning later (splitting into an upper/lower pair to describe real
directional asymmetry), may not.

## 4. `run_pipeline()` empty-`gene_dir` guard

Real bug hit live: `chunk_paths()` just `glob()`s `gene_dir` for `*.json` —
if the directory is wrong (stale relative path after a cwd change, typo,
genes landed somewhere else), the main loop in `run_pipeline()` simply never
executes, and an empty `problems == {}` return looks *identical* to a
genuinely clean run of the real corpus. Fixed: an empty `gene_dir` is now a
hard `RuntimeError` naming the exact path searched and the actual
`os.getcwd()`, not a silent no-op.

## 5. GPU-accelerated baseline-generation pipeline (the big one)

This is most of the session. Full design/investigation record (all
findings, verified against the real code, including things later corrected
mid-plan) lives in `~/.claude/plans/imperative-frolicking-alpaca.md` — not
fully repeated here, but the shape:

**Kmer first** (`gpu_kmer_count.py`): VRAM-aware batching — concatenates
many isoforms into one flat buffer per kernel launch instead of dispatching
one tiny launch per isoform, sized from *actually free* GPU memory
(`cupy.cuda.Device().mem_info` — a real bug caught live: it's a property,
not a method). Measured ~20x speedup (13.12s → 0.63s, 300 genes, dev
machine's RTX 3050).

**Then the other 4 tests** (`gpu_rare_codon_count.py`,
`gpu_codon_usage_count.py`, `gpu_codon_pair_bias_count.py`,
`gpu_gc_count.py`), which used to be pure-Python, zero-vectorization loops
in `baseline.py`. Share a new `gpu_corpus_batch.py` utility module
(VRAM-aware batch sizing, ragged-isoform concatenation with boundary
masking so no k-mer/window ever spans two genes, per-gene segment-mean
reduction via `bincount`). Every new module verified byte-for-byte
(`pytest.approx` for float-reduction fields, exact for everything else)
against `baseline.py`'s existing functions, on both numpy and real GPU
hardware — this is what caught:
- An empty-batch edge case in the shared concat utility.
- A genuine tie-breaking limitation in the new majority-vote function
  (documented, not "fixed" — ties are inherently unspecified in
  `baseline.py`'s own original algorithm too, see finding below).
- A cupy memory-pool-cleanup step that wasn't defensive enough and crashed
  an entire sequential-group chunk the first time a GPU-unavailable
  fallback happened inside it (see below).

**`baseline_pipeline.py` changed shape**: all 5 tests now run in wave 2,
sequentially inside ONE shared forked process per chunk
(`_run_sequential_group()`), not the old wave-1-concurrent-processes shape.
Deliberate, Luke's explicit call after being asked: once every test is
GPU-capable, N concurrent processes means N CUDA contexts fighting over one
GPU's VRAM — more contention risk than real gain, since CUDA serializes
kernel execution on one device across contexts anyway. Each spec is still
individually try/excepted inside the shared child so one test's failure
doesn't stop its siblings (verified with real forked processes, including
the memory-pool-cleanup bug above, caught live and fixed by broadening its
exception catch).

**Two real findings surfaced while scoping this, handled two different
ways**:

1. **Fixed**: `compute_codon_usage_analysis`/`compute_codon_pair_bias_analysis`/
   `compute_gc_analysis` in `baseline.py` were silently dropping the last
   mathematically-valid window in every isoform (the old `range(0,
   max(len-winsize, 0))` "one short" convention). Luke's explicit call on
   review: this was itself the bug ("poor code writing on my part"), not
   something to preserve — fixed to match `compute_rare_codon_analysis`'s
   already-correct full-window convention, and the new GPU counting modules
   match the corrected convention throughout.
2. **NOT fixed, deliberately left open**: `baseline.py`'s counting-side
   majority-location-bucket vote (raw-tag-vote-then-fold: vote among F/T/I/S
   first, fold only the winner) and `change_vector.py`/`gpu_change_vector.py`'s
   scoring-side vote (`majority_window_bucket()`, fold-then-vote: fold every
   tag first, merging S and I into the same bin, *then* vote) are two
   genuinely different algorithms, confirmed to disagree in real, non-tie
   cases (concrete counter-example: 5×S + 4×I + 6×F — raw vote picks F
   outright, fold-first vote gives S+I=9 beating F=6). `gpu_kmer_count.py`'s
   *counting* side already, independently, picked the *scoring* convention
   (calls `majority_window_bucket()`), so it already disagreed with its own
   stated oracle before this session even started — a real, live,
   previously-undetected discrepancy currently affecting the actual
   `Standards/KmerAnalysis.json` this pipeline generates, invisible in every
   existing test because `conftest.make_synthetic_genes()` never generates
   `'S'` tags. All 8 call sites across `baseline.py`, `change_vector.py`,
   `gpu_change_vector.py`, `gpu_kmer_count.py` are now tagged with
   cross-referencing comments (including correcting a prior comment in
   `change_vector.py` that mischaracterized this as "tie-break only", which
   it isn't). New `gpu_gc_count.py` deliberately does NOT repeat
   `gpu_kmer_count.py`'s mistake — uses a new, correct
   `gpu_corpus_batch.majority_raw_tag_bucket()` instead. **Whether to unify
   the two conventions is an open decision, not made here** — unifying
   would shift GC/Kmer scores for any real gene with S-tagged codons,
   which could matter for already-completed weight calibration (§3 above).
   Full detail: memory `majority_vote_bucket_discrepancy.md`,
   backlog item 8 in `future_work_items.md`.

## 7. Real-run diagnosis: progress logging + threaded gene loading

Luke ran the (then-just-synced) notebook for real in Colab and reported 20
minutes with no visible GPU usage. Root cause confirmed (not just guessed,
via checking small VRAM spikes + RAM fluctuation pattern Luke reported,
consistent with per-chunk load-then-free): `run_pipeline()` used to print
*nothing at all*, anywhere, for an entire run, and gene-loading off
Drive-mounted storage is genuinely slow (~1-2s/gene, confirmed earlier this
project — network/FUSE round-trip latency, not local CPU work). With zero
output there was no way to distinguish "working normally, just I/O-bound"
from "hung" from "silently falling back to CPU".

Two fixes:
1. **Visibility**: `run_pipeline(..., verbose=True)` (new default-on
   parameter) prints per-chunk-load and per-spec-dispatch progress with
   timing, flushed immediately (Colab/non-tty stdout can otherwise buffer
   and delay output).
2. **The real fix**: `gene_io.load_gene_chunk()`/`load_genes()` now load
   concurrently via a thread pool (`max_workers`, default 8,
   `ThreadPoolExecutor.map()` — preserves order despite out-of-order
   completion) instead of one file at a time. Key insight, not obvious:
   the ~1-2s/gene cost is network/FUSE *latency*, not CPU work — a thread
   blocked on a file read releases Python's GIL while it waits, so many
   reads can be in flight on the network simultaneously even on Colab's
   single CPU core. This is why threads (not multiprocessing, which is
   what the CPU/GPU-bound compute steps in `baseline_pipeline.py` correctly
   use instead) are the right tool specifically for this step. Verified
   with simulated per-file latency: 7.7x speedup at 8 workers against 40
   files with 50ms artificial delay each.

   This same fix applies for free to whatever loads the full corpus for GA
   ngram training (`codon_ngram.build_codon_ngram_model()`'s caller, e.g.
   `scripts/colab_stress_test.py`'s `gene_io.load_genes(...)` call) — no
   changes needed there, since the new parameter defaults on.

Notebook gained a `LOAD_WORKERS = 8` config knob to match.

## Verification methodology used throughout this session

Consistent pattern, worth continuing: every new GPU-batched module was
checked against its pure-Python reference on real, live data (or realistic
synthetic data reproducing a specific edge case) on BOTH the numpy backend
(cheap, always runs) AND real GPU hardware (this dev machine's RTX 3050,
via WSL) before being trusted — this caught real, non-hypothetical bugs at
every stage (the `mem_info` property-vs-method bug, the empty-batch bug,
the majority-vote tie-breaking discovery, the memory-pool-cleanup crash).
Don't skip the real-GPU check on the assumption that "numpy passing implies
cupy-correct" — it doesn't, provably, multiple times this session.
