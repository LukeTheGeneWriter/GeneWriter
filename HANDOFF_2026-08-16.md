**What changed, structurally:** `downloadGenePackagesAndProcess` now loops
over batches (`_chunked(gene_ids, batch_size)`) instead of individual gene
IDs. Per batch: one `datasets download gene gene-id <id1> <id2> ...`
subprocess call (multiple space-separated IDs — general CLI knowledge, not
live-verified), one `sleep(5)` (**unchanged, still fires — just once per
batch instead of once per gene, per the user's explicit instruction not to
touch it**), one unzip, then a per-gene inner loop that reuses the existing,
unmodified per-gene processing logic (try/except safety net, exon-size
guards, `problem_genes.json` logging, `saveNaturalGeneObj` — all untouched).
`clearDownloadDirectory()` now fires once per batch (after every gene in it
is processed), not per gene, since the extracted data is shared.

**Three things this implementation had to guess at, since none of them are
checkable without live NCBI data** — each has an explicit runtime check and
a logged, safe fallback rather than a silent wrong answer:
1. **Zip layout**: assumes a batch download still unpacks to a single
   `ncbi_dataset/data/...` root (same as single-gene), with
   `data_report.jsonl`/`product_report.jsonl` holding one line per gene. If
   this is wrong, the missing-file check right after unzip will fire and log
   it clearly, and the whole batch gets marked as problem genes rather than
   silently reading garbage.
2. **Row selection**: added `_row_for_gene()` + `_GENE_ID_COLUMNS = ('geneId',
   'gene_id', 'gene.geneId', 'gene.gene_id')` to find each gene's own row in
   the batch's merged `data_report`/`product_report` dataframes. If a batch
   has only one row it's used directly (handles BATCH_SIZE=1 and edge cases
   without needing the id column at all). If no candidate column matches for
   a multi-row batch, it logs a warning naming the actual columns found and
   skips that one gene (recorded to `problem_genes.json`) rather than
   guessing which row is whose.
3. **gSeq (whole-gene DNASequence)**: previously just `genomes[0].seq`
   (correct when genomes has exactly one record, i.e. per-gene downloads).
   Now resolves by matching the accessions each gene's own isoforms'
   `genomicAccessionVersion` values reference (collected during the existing
   per-isoform exon-extraction loop) against the batch's merged `genomes`
   list. `getSeqFrom()` itself needed **no changes** — it already searches
   the full `genomes` list by accession per exon set, which works identically
   whether that list holds one gene's records or a whole batch's. If no
   accession match is found, falls back to `genomes[0]` with a warning —
   note this only affects the gene-level `DNASequence` convenience field, not
   the exon/codon data itself (which is matched independently per isoform
   regardless).

## RAM monitor (added on top of batching, same session)

**DONE.** User asked for a RAM trip at 90% with a two-tier response: if a
*batch* is at risk of crashing the session, fall back to downloading each of
its remaining genes individually; if a *single* gene is still too large even
on its own, skip it. Implemented in the same
`downloadGenePackagesAndProcess()`:

- `_RAM_TRIP_PERCENT = 90.0` and `_ram_percent()` (wraps
  `psutil.virtual_memory().percent`, auto-installing `psutil` via `!pip
  install --quiet psutil` if the Colab runtime doesn't already have it —
  it almost certainly does).
- The function was refactored into three pieces to make the two-tier
  fallback expressible without duplicating logic:
  - `_download_and_parse(ids, label, data_directory)` — the download +
    sleep(5) + unzip + parse step, pulled out so it can be called once for
    a whole batch OR once for a single gene.
  - `_process_gene(gene_id, gene_row, prod_row, proteins, genomes,
    problem_genes)` — the actual per-gene NaturalGene-building logic
    (unchanged from the batching pass), now callable independent of how
    many genes were downloaded alongside it.
  - `downloadGenePackagesAndProcess()` itself now just orchestrates:
    download/parse a batch, then loop its genes one at a time, checking RAM
    before each.
- **The fallback itself is recursion**: when RAM trips on a multi-gene
  batch, the remaining genes in that batch are each re-run through
  `downloadGenePackagesAndProcess([g], data_directory, batch_size=1)` —
  the very same function, called with a length-1 gene list. That's what
  makes it hit the "single gene" branch instead of "batch" on the retry
  (`len(batch) > 1` is false for a length-1 batch), which is also what
  makes a single gene that's *still* too large just get skipped rather than
  attempting a fallback-of-a-fallback. Before recursing, the just-failed
  batch's `proteins`/`genomes`/`df_final`/`df_final1` are explicitly
  `del`ed and `gc.collect()`ed — that shared, potentially-dozens-of-genes
  in-memory data is the most likely actual contributor to the RAM pressure,
  and it needs to actually be freed before downloading more.
- `downloadGenePackagesAndProcess()` now **returns** the list of
  problem/skipped gene IDs (it used to return nothing) — needed so a
  recursive call's own problem genes get merged into the caller's list
  rather than each recursive call silently overwriting
  `problem_genes.json` with just its own short list.
- Verified via a standalone control-flow simulation (all I/O stubbed out,
  scripted RAM-percent sequences) covering: no RAM pressure (baseline),
  mid-batch trip → individual fallback → all genes eventually processed,
  a fallback gene that's *still* too large → skipped and logged, and a
  batch whose download itself fails → whole batch logged, nothing
  processed. All four passed. This validates the recursion/looping logic
  itself; it does **not** validate `psutil` actually being present/accurate
  in the real Colab runtime, which — like everything else marked NOT
  LIVE-VERIFIED above — needs a real run to confirm.
- Not done, and not asked for: no check *during* a single gene's
  processing (only before each gene starts). If one particular gene is
  large enough to blow RAM by itself mid-processing, this won't catch it
  mid-flight — it'll be caught by the *next* gene's RAM check instead
  (after the damage, if any, is already done). This matches the user's own
  framing of the two-tier design (batch → individual → skip) and wasn't
  something they asked for a finer-grained version of; flagging in case a
  live run shows it's needed.

   distribution_fit.py`): the user noticed CodonPairBias baseline data
   looks Boltzmann-shaped, not Gaussian, and the old `(x-mean)/std` z-score
   — squared for scoring — silently misrepresents rarity for skewed
   distributions (asymmetric deviations scored as if symmetric). Built
   `fit_normal_transform()`: auto-selects the best-fitting distribution
   (norm/expon/gamma/lognorm/skewnorm via AIC) and reduces it to a
   normal-scores lookup table (`FittedDistribution.transform`/
   `transform_array`, xp-compatible for numpy+cupy). Wired into
   `change_vector.py` (`cached_normal_transform`, alongside the old
   `cached_mean_std`), `gpu_change_vector.py`'s batched terms, and
   `weight_calibration.py`'s `natural_deviation_zscores`. When `norm` wins
   the fit, this is bit-identical to the old formula (verified). Updated
   `tests/test_change_vector_reference.py`, `test_weight_calibration.py`,
   `test_ga.py` (fixtures that used pathological 2-point-mixture arrays
   were switched to real Gaussian samples). New `tests/
   test_distribution_fit.py`. Full suite passing (307 tests as of this
   change).

4. **GC term redesign**: per the user's design, replaced the old
   multiplicative `gc1/gc2/gc3-by-bucket` signal (which turned out to be a
   whole-candidate aggregate that barely moved when scoring synonymous
   alternatives — see `directed_evolution_batch()`'s own docstring) with an
   **additive per-sequence GC deviation** (one scalar via `GCAnalysis.
   gcPerGene`, added to the existing local windowed signal), gated by a
   single "is any base at this position mutable" flag. New formula:
   `GC_term[i] = mutable[i] * (per_codon[i] + seq_deviation)`. Changed in
   `change_vector.py`'s `_gc_term` and `gpu_change_vector.py`'s
   `batch_gc_term`. Removed the now-dead `taggedGC1/2/3`-by-bucket
   machinery and `TAG_TO_BUCKET`/`_LOCATION_BUCKET_NAMES` imports/constants
